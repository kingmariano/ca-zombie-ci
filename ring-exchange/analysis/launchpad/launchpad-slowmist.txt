1 Executive Summary
On 2024.11.27, the SlowMist security team received the team's security audit application for RingLaunchpad,
developed the audit plan according to the agreement of both parties and the characteristics of the project, and ﬁnally
issued the security audit report.
The SlowMist security team adopts the strategy of "white box lead, black, grey box assists" to conduct a complete
security test on the project in the way closest to the real attack.
The test method information:
Test method Description
Black box testing Conduct security tests from an attacker's perspective externally.
Grey box testing Conduct security testing on code modules through the scripting tool, observing the
internal running status, mining weaknesses.
White box
testing
Based on the open source code, non-open source code, to detect whether there are
vulnerabilities in programs such as nodes, SDK, etc.
The vulnerability severity level information:

project, and it is strongly recommended to ﬁx the critical vulnerabilities.
High High severity vulnerabilities will aﬀect the normal operation of the DeFi project. It is
strongly recommended to ﬁx high-risk vulnerabilities.
Medium Medium severity vulnerability will aﬀect the operation of the DeFi project. It is
recommended to ﬁx medium-risk vulnerabilities.
Low
Low severity vulnerabilities may aﬀect the operation of the DeFi project in certain
scenarios. It is suggested that the project team should evaluate and consider whether
these vulnerabilities need to be ﬁxed.
Weakness There are safety risks theoretically, but it is extremely diﬃcult to reproduce in engineering.

4.3 Vulnerability Summary
[N1] [Medium] Malicious creation of liquidity
Category: Design Logic Audit
Content
In the RingLaunchpad contract, users can create a new ERC20 Token contract through the publicly callable function
deploy, and create a new wrappedToken contract for this new ERC20 Token contract. And use this wrappedToken
contract and its wrappedWETH as a pair to add a token pair in UniswapV2. Because it is publicly callable and there
is no other cost except the gas fee, malicious users can call the deploy function multiple times and cast
wrappedWETH to add token pairs. The deployWETH and deployETH functions can also be deployed by passing
buyAmount or msg.value as 0 to the deploy function. Although there is an upper limit on the pairAmount,
wrappedWETH can be over-minted through multiple calls. Also, the minting Token contract does not check the name
and symbol restrictions. Then this malicious user can cast multiple token pairs with the same name and symbol but

===== PAGE 8 =====
diﬀerent addresses to confuse the user market.
Code location:
contracts/RingLaunchpad.sol#L48-L84, L93, L107
    function deploy(
        string memory name,
        string memory symbol,
        uint256 pairAmount
    ) public virtual nonReentrant returns (address token, address wrappedToken) {
        if (
            ...
        }
        IFewWrappedToken(wrappedWETH).mint(address(this), pairAmount);
        token = address(new Token(name, symbol));
        wrappedToken = IFewFactory(wrappingFactory).createToken(token);
        ...
        IUniswapV2Router02(uniswapRouter).addLiquidity(
            ...
        );
        emit TokenDeployed(msg.sender, token, wrappedToken, pairAmount);
    }
    function deployWETH(
        ...
    ) external virtual returns (address token, address wrappedToken) {
        (token, wrappedToken) = deploy(name, symbol, pairAmount);
        if (buyAmount > 0) {
            IERC20(weth).safeTransferFrom(msg.sender, address(this), buyAmount);
            _buyTokens(recipient, wrappedToken, buyAmount);
        }
    }
    function deployETH(
        ...
    ) external payable virtual returns (address token, address wrappedToken) {
        (token, wrappedToken) = deploy(name, symbol, pairAmount);
        if (msg.value > 0) {
            IWETH(weth).deposit{value: msg.value}();
            _buyTokens(recipient, wrappedToken, msg.value);
        }
    }

Solution
It is recommended to authenticate the deploy function, and call the deploy function to create and add token pairs
only when a swap call is needed in the   deployWETH and deployETH functions. At the same time, add restrictions
that limit the name and symbol to be diﬀerent to prevent confusion in the token market.
Status
Acknowledged; After communicating with the project team, they stated that this is a known feature. Users need to
pay gas to create tokens, so it is ﬁne. Duplicate names and symbols will also happen.
[N2] [Low] Receive can lock users’ native tokens
Category: Others
Content
There is a receive function in the RingLaunchpad contract so that the contracts can receive native tokens. However,
the receive function can lock users’ native tokens when users transfer the native token in these contracts by mistake.
Code location:
contracts/RingLaunchpad.sol#L148
    receive() external payable {}
Solution
It’s recommended to add addresses that can send the native tokens in the contract in the require check logic in the
receive() function.
Status
Acknowledged
[N3] [Suggestion] Missing zero address check
Category: Others
Content
When setting the address in parameter constructor initialization, it is not checked whether the set address is 0
address.

[N4] [Suggestion] Missing the event records
Category: Others
Content
In the RingLaunchpad contract, the owner role can modify the threshold through the setThreshold function, but there
is no event record.
Code location:
contracts/RingLaunchpad.sol#L143-L146
    function setThreshold(uint256 _threshold) external onlyOwner nonReentrant {
        if (_threshold > MAX_THRESHOLD) revert InvalidParameters();
        threshold = _threshold;
    }
Solution
It is recommended to record events when sensitive parameters are modiﬁed for self-inspection or community review.

[N5] [Suggestion] Redundant code
Category: Others
Content
In the RingLaunchpad contract, the owner role can modify the threshold through the setThreshold function, but there
is a nonReentrant check in the function's modiﬁer. The function only needs to modify this parameter and there is no
subsequent operation, so the nonReentrant modiﬁer is redundant.
Code location:
contracts/RingLaunchpad.sol#L143-L146
    function setThreshold(uint256 _threshold) external onlyOwner nonReentrant {
        if (_threshold > MAX_THRESHOLD) revert InvalidParameters();
        threshold = _threshold;
    }
Solution
It is recommended to clarify the business logic implementation, and if it is redundant code, it is recommended to
remove it from the contract to save gas.
Status
Fixed
[N6] [Information] Predictable Token Deployment Address
Category: Race Conditions Vulnerability
Content
In the deploy function, the new Token(name, symbol) creates a token whose contract address is determined based
on the creator's address and nonce. This address can be predicted, making it vulnerable to front-running attacks.
Code location:
contracts/RingLaunchpad.sol#L64

===== PAGE 12 =====
        token = address(new Token(name, symbol));
Solution
It is recommended approach is to leverage the CREATE2 opcode combined with a salt value to deploy contracts.
Status
Acknowledged; After communicating with the project team, they stated that they will warn users to double check the
actually created token&pool address, never pre-calculate the address and use it as a pre-assumption.
